# HU-019: Reclasificación de Caso

## AC-1: Cambiar Categoría
**Given** Soporte ve que es comercial, no técnico  
**When** invoca `reclasificar_caso_sin_licencia()`  
**Then**
- Caso cambia de "Soporte Técnico" a "Comercial"
- Notificación va a equipo Comercial
- Audit log registra quién reclasificó, timestamp, cambio anterior

## AC-2: Caso No Existe
**Given** Soporte intenta reclasificar un caso ID que no existe  
**When** invoca `reclasificar_caso_sin_licencia(case_id)`  
**Then** devuelve "Caso no encontrado. ¿Verificaste el número de ticket?"

## AC-3: Caso Ya Reclasificado
**Given** Caso fue reclasificado hace 5 min a Comercial  
**When** Soporte intenta reclasificar de nuevo a Técnico  
**Then** devuelve "Caso ya fue reclasificado a Comercial. ¿Quieres reversar el cambio?" + permite reversa

## AC-4: Race Condition (Reclasificaciones Simultáneas)
**Given** Dos agentes de Soporte intentan reclasificar el mismo caso al mismo tiempo (ambos leen "Técnico")  
**When** ambos invocan `reclasificar_caso_sin_licencia()` con categorías diferentes (uno → Comercial, otro → Escalación)  
**Then**
- Base de datos usa transacción serializable (o version lock)
- El primer write gana; el segundo obtiene: "Caso fue reclasificado por otro usuario. Recarga para ver cambio actual"
- Audit log registra ambos intentos con timestamp exacto y resultado (won/lost)

## Dependencias
- **HU-015:** En tests, caso pre-cargado via fixture (no bloqueado por entrega de HU-015). En integración: ambas en Sprint 2.
- **EP-002:** Error handling para reversals y auditing
- **EP-003:** Audit log de cambios

## Nota de Independencia
Para desacoplar de HU-015, AC-1/AC-2/AC-3 usan fixture de caso `caso_id=12345` (pre-cargado en test DB) en lugar de depender de que HU-015 haya creado un caso real. Cuando HU-015 se implementa, ambas historias conviven en el mismo sprint; tests pasan con fixture, integración pasa con caso creado por HU-015.
